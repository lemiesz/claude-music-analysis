Field report · DJ library engineering

Organizing an entire rekordbox library with scripts, Discogs, and a neural network

Over about a week, an unwieldy rekordbox collection — 160 playlists, thousands of untagged tracks, a mountainous “no category” pile — was restructured, enriched with real metadata, audio-analyzed with ML models, and wired into the hardware workflow (XDJ Track Filter, Matching, USB export). Everything was done with Python scripts against the rekordbox database directly, with Claude Code doing the heavy lifting. This is what was built and how you could build the same thing.

Part 1Working the library with Claude: the raw mechanics

Everything below rests on one fact: a rekordbox library is just a database. Rekordbox 6/7 stores every track, playlist, tag, comment, and BPM in an encrypted SQLite file (master.db under ~/Library/Pioneer/rekordbox), and the Python library pyrekordbox (≥ 0.4.4, which ships the decryption key) opens it read/write.

The working setup had two halves:

  • Reading — an MCP server. A small rekordbox MCP server let Claude query the library conversationally: search tracks, list playlists, inspect play history, find broken file references. All exploration and planning happened this way.
  • Writing — deterministic scripts. Claude never “hand-edited” the database. Every change was a Python script it wrote, which was reviewed in dry-run mode first, then re-run with --apply. Scripts are idempotent, so re-running one is always safe.

Safety: the rules every write script follows

The contract: back up master.db automatically before touching anything · refuse to run while rekordbox is open · dry-run by default, --apply to commit · only ever fill empty fields, never overwrite existing metadata · verify track counts after every run. Final tally after ~15 write operations: every track that went in came out — verified by count each time — and a folder of timestamped master.db.backup-* files that were never needed.

Two mechanics-level gotchas worth knowing before you write anything: pyrekordbox commits land in SQLite’s write-ahead log, so run PRAGMA wal_checkpoint(TRUNCATE) after committing or rekordbox may read a stale tree; and always fully quit and relaunch rekordbox to see changes.

What the mechanics enabled first: structure

The first project was organizational. The library went from 20 messy top-level items to 12: eight genre folders (house, techno, trance, dnb, bass, psy, hip-hop, disco) plus four non-genre ones (partner’s crate, gig sets, _unsorted, _system), all reparented via pyrekordbox’s move_playlist. The organizing philosophy:

  • Folders and playlists = crates and sets. Curation and order. Genre browsing, gig prep.
  • Tags and native fields = attributes. Genre, label, energy, mood — things you filter by.
  • Smart playlists = the bridge. Auto-built crates from tag combinations.

Tags were then derived from structure so nothing was entered twice: a Genre My Tag from top-level folder membership, Label My Tags from the old record-label crates, Energy from existing energy playlists. Because CDJs don’t show My Tags everywhere, every tag is also mirrored into the Comment field as #hashtags — visible and searchable on any player.

One early lesson: verify before merging “duplicate” playlists. Two playlists with similar names and identical track counts shared zero tracks; another pair was genuinely identical. Count-match ≠ duplicate — compare track IDs.

USB and hardware management is scriptable too

The same database-first approach extends past the laptop:

  • My Tag banks: XDJ/CDJ hardware Track Filter only displays 4 My Tag banks. Nine accumulated banks were consolidated down to Genre / Energy / Vibe / Label by re-parenting tag rows — track assignments follow automatically.
  • Export databases: a USB stick exported from rekordbox carries its own databases (exportLibrary.db, and the classic exportExt.pdb that older players read). Both can be written directly when rekordbox’s own sync falls short — more on why in Part 3.

Part 2Filling in the metadata: Discogs and Spotify

Structure only helps if tracks carry data worth filtering on — and most tracks had no genre, label, or year. A pipeline (analyzer.py) fetches real metadata from external APIs into a local SQLite cache (metadata.sqlite), decoupling the slow network part from the database write:

fetchQuery external APIs per track. Slow, rate-limited, incremental and resumable — safe to run for days.
→
metadata.sqliteLocal cache: matches, confidence scores, a generic feature table so new sources need no schema change.
→
applyWrites into rekordbox with --min-confidence gate, fill-empty only, full provenance log of every applied value.

Discogs: the workhorse

Discogs matches by artist/title search, upgraded to a catalog-number search whenever a [CATNO] appears in the title — a big accuracy win for white-label and promo material. Results: 78% of fetched tracks matched. Applied at confidence ≥ 0.6: thousands of genres, labels, release years, and catalog numbers, all into previously empty fields. Discogs is free but hard-capped at 60 requests/min, so the full fetch ran in the background over about a day.

Every applied value is logged with track, field, value, source, and confidence — so weak fills can be found and upgraded later when a better source appears.

Spotify: what its API can still do (and what it can’t)

Spotify’s Web API is still useful for metadata, with one big caveat:

  • What works: search by ISRC — the standard recording identifier embedded in store-bought files — for an exact track match, then pull the artist’s genre list and the release date. Free client-credentials auth, no user login needed.
  • What’s gone: the audio-features endpoint (energy, danceability, valence…) was deprecated for new apps in November 2024 and returns 403. The fetcher probes it once, marks it dead, and moves on. There is no hosted replacement — which is exactly why Part 3 exists.

In this pipeline Spotify is a secondary source registered alongside Discogs in the same SOURCES table — adding a source is one function that takes a track and returns values.

Part 3Analyzing the sound itself: embeddings, clustering, Matching

Text metadata tells you what a track is called; it can’t tell you what it sounds like. With hosted audio analysis gone, the answer was local ML, using the MTG (Universitat Pompeu Fabra) open-source models:

  • discogs-effnet — a CNN trained on Discogs data. Audio in, a 1280-dimensional embedding out, plus scores for 400 sub-genres.
  • Mood heads on top of the embedding: happy, sad, aggressive, relaxed, party, danceability.

The trick that made it fast: full-file decoding was the bottleneck (~1.8 s/track), not the neural net. So each track is sampled as six 15-second segments spread from 5% to 90% of its length (catches both build-ups and drops), decoded with ffmpeg, run through the model in parallel across CPU cores. ~5.5 tracks/sec — the whole library in under 80 minutes. Embeddings are stored as blobs in SQLite, so every downstream feature is free — nothing ever needs re-analyzing.

The mood scores became My Tags: an Energy axis (warmup / groovy / driving / peak, from quartiles of the “aggressive” score — the best-spread feature) and a Vibe axis (happy, chill, dark, euphoric, hypnotic, melancholic, feelgood — rule combinations over the mood scores).

Auto-sorting the “no category” pile

The to-file pile got sorted three ways at once (add-only — originals untouched): by-genre, by-BPM, and by-sound — cosine k-means over the embeddings (K=26), each cluster named by its dominant distinctive Discogs sub-genre (cloud-rap, bassline, psy-trance, halftime…), then tempo-split into BPM leaves. The naming rule: if a cluster can be meaningfully named it gets its own folder; otherwise it folds into the nearest genre folder — no hip-hop-2, hip-hop-3 junk.

A subtle fix that mattered: feel-BPM. Rekordbox tags half/double-time wrong constantly (cloud rap “at 140” feels like 70; some house “at 62” feels like 124). Genre-anchored folding rules corrected hundreds of tracks before bucketing, and a separate script permanently halved the stored BPM where the ML tempo estimate confirmed half-time feel.

A sound map of the whole library

The embeddings power a local Dash/Plotly web app: UMAP projects every analyzed track onto a 2-D map, colored by genre, cluster, or mood. Click any track and you get its nearest sonic neighbors (“sounds like” list, cosine similarity) and can play the audio in the browser. Great for digging, finding mislabeled tracks, and sanity-checking the clusters.

Building Matching — and getting it onto the players

Rekordbox’s built-in Matching (track-suggestion) feature was populated programmatically from the same embeddings: pairs with cosine similarity ≥ 0.90, BPM-compatible within 8% (1:1, 2:1 or 1:2), a bonus for Camelot-compatible keys, top 6 partners per track. The threshold matters — in this embedding space 0.85 is close to the random-pair 99th percentile and would produce millions of junk pairs.

Getting those pairs onto a USB stick took the direct-write mechanics from Part 1: rekordbox’s device sync ignores Matching rows written outside its UI (its change ledger never saw them), so scripts write them straight into the stick’s own databases — exportLibrary.db for modern players, and the classic exportExt.pdb format that the XDJ-XZ actually reads (deck-verified). Both scripts run the same dry-run/backup/apply contract.

Part 4Keeping it alive: the ingest pipeline

All of the above would rot in a month if new imports needed manual care. One incremental script (ingest_new_tracks.sh) runs the whole chain for new tracks only: analyze the new audio (rekordbox can stay open) → dry-run → apply (embeddings, BPM half-time fix, Genre/Energy/Vibe tags, no-category buckets, Matching pairs — in that order, since tags and buckets depend on corrected BPM). Nothing is ever recomputed for old tracks, so ingesting a batch of new imports takes minutes.

Part 5How to recreate this

You don’t need every part — each stands alone. Rough order of effort-to-payoff:

  1. Set up access. Python 3.11+, pip install pyrekordbox (≥ 0.4.4). Confirm you can read your library. Write a backup helper before anything else, and adopt the safety contract above verbatim.
  2. Decide your structure on paper first. Folders = crates, tags = attributes. Pick your top-level genre folders and your 4 My Tag banks (hardware limit!) before scripting anything.
  3. Script the reorg and derived tags. move_playlist for folders; derive Genre tags from folder membership; mirror tags into Comments as hashtags for CDJ visibility.
  4. Enrich from Discogs. Free API token, 60 req/min. Cache results in your own SQLite; separate fetch from apply; gate on match confidence; fill empty fields only. Add Spotify’s ISRC lookup as a second source for artist genres and release dates.
  5. Audio analysis. Get the free MTG essentia models (discogs-effnet + mood heads). They run in plain TensorFlow — you don’t need the full essentia C++ build for inference if you replicate the mel-spectrogram frontend. Sample a few short segments per track instead of decoding whole files. Store embeddings; everything downstream is free after that.
  6. Cluster, map, match. scikit-learn k-means / UMAP / cosine similarity on the embeddings — this is standard Python data tooling from here.

The scripts and a set of importable Claude Code skills distilled from this project live in the claude-music-analysis GitHub repository, alongside this report.

What was learned the hard way

Commits land in the WAL. After writing via pyrekordbox, run PRAGMA wal_checkpoint(TRUNCATE) or rekordbox may read a stale tree. Fully quit and relaunch rekordbox to see changes.
Spotify’s audio-features API is gone for new apps (since Nov 2024). Local models are the replacement — and they’re better, since you get raw embeddings.
Essentia has no arm64 pip wheel. On Apple Silicon, either build it from source or skip it: the TensorFlow models run fine in plain pip install tensorflow.
Stored BPM lies. Expect hundreds of half/double-time mistags in any big library. Cross-check against an independent tempo estimate before trusting BPM for anything.
Device sync has a ledger. Rows written to master.db outside the rekordbox UI may never reach an exported USB via incremental sync — write the export databases directly when it matters.
Playlist merges need proof. Compare actual track IDs, not names and counts.
Keep external files mounted. Audio analysis needs the actual files (here, ~90% lived on an external SSD); metadata enrichment doesn’t.
